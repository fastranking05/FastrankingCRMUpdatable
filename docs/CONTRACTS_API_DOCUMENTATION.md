# Contracts API Documentation

## Overview

The Contracts API stores contract documents as JSON (the complete frontend design/payload) in the `contracts` table and can email a frontend-generated contract PDF to a recipient.

Each contract has an auto-generated `document_id` (UUID) and is linked to a proposal (`proposal_id`) and a business (`followup_business_id`).

## Base URL

```
/api/contracts
```

## Authentication & Permissions

All endpoints require JWT authentication. Contracts use the **Proposals** module permissions.

| Permission | Description |
|------------|-------------|
| `Proposals,read` | List and view contracts |
| `Proposals,create` | Create contracts and send them by email |
| `Proposals,update` | Update contracts |
| `Proposals,delete` | Delete contracts |

---

## API Endpoints

### 1. List Contracts (GET)

**Endpoint:** `GET /api/contracts`

#### Query Parameters

| Parameter | Type | Description |
|-----------|------|-------------|
| `proposal_id` | string | Filter by proposal ID (`FRPR...`) |
| `followup_business_id` | integer | Filter by business |
| `created_by` | integer | Filter by creator user ID |
| `per_page` | integer | Results per page (default: `15`) |
| `cursor` | string | Cursor token for pagination |

---

### 2. Create Contract (POST)

**Endpoint:** `POST /api/contracts`

#### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `proposal_id` | string | Yes | Existing proposal ID (`FRPR...`) |
| `followup_business_id` | integer | Yes | Business the contract belongs to |
| `document` | object | Yes | Complete frontend design JSON (any structure) |

#### Example

```json
{
  "proposal_id": "FRPR00000001",
  "followup_business_id": 12,
  "document": {
    "pages": [],
    "fields": {},
    "styles": {}
  }
}
```

#### Response

`201 Created` — the contract object including the generated `document_id` UUID.

---

### 3. Get Contract (GET)

**Endpoint:** `GET /api/contracts/{id}`

`{id}` accepts either the numeric `id` or the `document_id` UUID.

---

### 4. Update Contract (PUT / POST)

**Endpoints:** `PUT /api/contracts/{id}` or `POST /api/contracts/{id}`

All fields are optional (`sometimes` validation): `proposal_id`, `followup_business_id`, `document`.

---

### 5. Delete Contract (DELETE)

**Endpoint:** `DELETE /api/contracts/{id}`

---

### 6. Send Contract (POST)

**Endpoint:** `POST /api/contracts/send`

Emails a contract to a recipient — either with the contract PDF attached, or with a **signing link** (the recipient e-signs online; no attachment needed). At least one of `pdf` or `sign_url` is required. Every send is logged in the `emails` table with type `contract`.

#### Request Body (multipart/form-data)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `pdf` | file | Conditional | Contract PDF generated by the frontend (max 10MB). Required if `sign_url` not sent |
| `sign_url` | string (URL) | Conditional | Public e-sign link shown in the email as a "Review & E-Sign" button. Required if `pdf` not sent |
| `email` | string | Yes | Recipient email |
| `business_id` | integer | Yes | Business the contract belongs to (email log) |
| `auth_person_id` | integer | No | Contact — used for the greeting name |
| `subject` | string | No | Defaults to `Contract - {business name}` |
| `message` | string | No | Email body text |
| `cc` | array | No | CC email addresses |
| `bcc` | array | No | BCC email addresses |
| `filename` | string | No | Attachment filename (defaults to `Contract.pdf`) |

#### Example

```bash
curl -X POST /api/contracts/send \
  -H "Authorization: Bearer {token}" \
  -F "pdf=@contract.pdf" \
  -F "email=contact@example.com" \
  -F "business_id=12" \
  -F "auth_person_id=45" \
  -F "subject=Contract - Acme Ltd" \
  -F "message=Please review and sign the attached contract."
```

#### Response

`200 OK`

```json
{
  "success": true,
  "message": "Contract sent successfully",
  "data": {
    "email_id": 12,
    "sent_to": "contact@example.com"
  }
}
```

| Error | Reason |
|-------|--------|
| 422 | Missing/invalid `pdf`, `email`, or `business_id` |
| 403 | No `Proposals,create` permission |
| 500 | Mail server error |

## Public E-Sign Endpoints (No Auth)

These power the client-facing signing page opened from the email link. No JWT or module permission required.

### 7. Get Contract Public (GET)

**Endpoint:** `GET /api/contracts/public/{documentId}`

Returns the contract record (including the `document` JSON with `deal`, `signatures`, `client_signed_at`) for rendering the e-sign page.

| Error | Reason |
|-------|--------|
| 404 | Invalid `documentId` |

### 8. Submit Client Signature (POST)

**Endpoint:** `POST /api/contracts/public/{documentId}/sign`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `signature` | string | Yes | Client signature (e.g. data-URL image or typed value) |
| `signed_at` | datetime | No | Defaults to server time |

Saves `document.signatures.client` and `document.client_signed_at`. After signing, the GET endpoint keeps returning the contract (read-only signed state).

| Error | Reason |
|-------|--------|
| 404 | Invalid `documentId` |
| 409 | Contract already signed — response includes `client_signed_at` |
| 422 | Missing `signature` |

## Notes

- Company name in the email signature comes from the `settings` table (`company_name`), falling back to `app.name`
- When `sign_url` is sent, no PDF is attached — the email shows a "Review & E-Sign" button plus the raw link
- When `pdf` is sent, the file is attached directly from the upload — nothing is stored on the server after sending
- Logged emails appear in the Emails module (`type: contract`) with to/cc/bcc and business reference
